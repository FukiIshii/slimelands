# slimelands

スライムが村人となり、合成・配合・ガチャで仲間を増やし、パーティーを組んでダンジョンに挑む
「村運営×スライム育成×半自動ダンジョン戦闘」のUnity 2Dゲームです。
[Stacklands](https://store.steampowered.com/app/1948280/Stacklands/)(カード積み重ね式の村運営)と、
「ゆっくり育てていってね」系の半自動ダンジョン戦闘を組み合わせたコンセプトで、個人開発中です。

![ダンジョン戦闘のスクリーンショット](docs/images/battle.png)

## 概要

- **村パート**: カードを重ねて合成(基本種スライムの入手)、既存スライム+素材で配合(上位種の入手)、
  ガチャ(全種が対象の抽選召喚)、育成(経験値によるレベルアップ)を行う
- **ダンジョンパート**: パーティーを編成して出発すると、ウェーブ単位で敵と自動的に遭遇する半自動戦闘になる。
  プレイヤーが操作できるのは「必殺技の発動」と「攻撃対象の指定」のみで、移動・通常攻撃は自動進行する
- 両パートはループする構成で、ダンジョンで得た素材を村に持ち帰って配合・進化・制作に使う

詳細なゲームデザインは [`docs/GDD.md`](docs/GDD.md)、実装の経緯・テスト結果・未決定事項は
[`docs/progress_report.md`](docs/progress_report.md) に記録しています。

## 設計で工夫した点

個人開発ではありますが、「後から仕様変更・機能追加しても壊れない」ことを一貫して優先し、
以下のような設計判断を行いました。

### 1. バランス値・マスタデータを一切ハードコードしない

スライム種族(`SlimeSpeciesData`)、配合・制作レシピ(`CardRecipeData`)、ガチャ排出率、タイプ相性
(`TypeAffinityData`)、ダンジョン定義(`DungeonData`)など、ゲームバランスに関わる値はすべて
ScriptableObjectのデータアセットとして持たせています。企画段階でバランス値が「要調整」である
ことが明らかだったため、コード変更なしにInspector上の数値調整だけで反映できる設計を最初に
ルール化しました([`CLAUDE.md`](CLAUDE.md) ルール2)。

### 2. バックトラッキングによる汎用レシピマッチング

配合・合成は「素材2種類以上の組み合わせ→結果」という形で、`CardIngredient`(特定カード指定、
または「スライムなら何でも良い」のようなカテゴリ指定)を複数持つ`CardRecipeData`として表現します。
判定ロジック(`CardRecipeData.TryAssign`)は、場に出ているカード群をレシピの素材枠に1対1で
割り当てられるかを再帰的に探索する、小さな制約充足アルゴリズムです。
「異なるタイプ同士」「同じタイプ同士」どちらの配合も、個別のif分岐を増やさずデータ追加だけで
対応できます。

### 3. 村とダンジョンの疎結合(イベント駆動の橋渡し)

村パートとダンジョンパートは直接参照を持たず、イベントと橋渡し役クラスだけで連携しています。
例えば、ダンジョンクリア(`DungeonRunController.OnDungeonCleared`)を村側の素材ドロップ処理
(`DungeonRewardHandler`)や進行状況管理(`DungeonProgressManager`)が個別に購読する構成のため、
どちらかの内部実装を変更しても他方に波及しません。ダンジョンの解放もツリー構造
(親ダンジョンを複数指定できる合流ノード対応)で、`DungeonProgressManager`が見た目に依存しない
純粋なロジックとして解放・クリア状態を判定します。

### 4. 種族マスタデータと個体差の分離

`SlimeSpeciesData`(種族ごとの不変データ、ScriptableObjectとして全個体で共有)と
`SlimeIndividual`(レベル・経験値・才能値・装備などの個体差)を明確に分離しています。
ScriptableObjectは参照が共有されるため、可変な個体差をそこに持たせると個体間でデータが
衝突するバグになります。これを避けるためにクラスを分けた、という判断をコード側のコメントに
明記しています。

### 5. シーン再読み込み・再コンパイルに強い自己修復設計

`CardStack`はカードの重なり順をTransform階層から`Awake()`で毎回再構築し、`CardController`も
エディタ上で直接配置されたカードの見た目・個体データをAwakeで自動補完します。実行時に構築する
キャッシュ値を信頼しすぎない設計です。
開発中に実際、この原則を破って `CardStack.Count`(実行時キャッシュ)を判定基準にした一括操作で
盤面のカードを誤って全削除してしまう事故がありましたが、シーン未保存だったため復旧でき、
以後は`transform.childCount`など一次情報を直接参照するルールに改めました。この経緯は
[`docs/progress_report.md`](docs/progress_report.md) に記録してあります。

### 6. テスト容易性を意識したAPI設計

ドラッグ&ドロップのようなマウス操作が絡む機能でも、実際の状態変更ロジック(装備/解除、
カード消費、経験値付与など)はUIの入力処理から独立した公開メソッドに切り出しています。
例えばアクセサリーの装備システムは `CardBoard.TryEquipAccessory` / `TryUnequipAccessory` という
公開APIとして実装し、マウス操作をシミュレートできない検証環境でも、Play Mode中にこれらのAPIを
直接呼び出してステータス反映・置き換え・解除の挙動を検証できるようにしています。

### 7. ドキュメント駆動のプロセス管理

[`docs/GDD.md`](docs/GDD.md) を仕様の正本、[`docs/progress_report.md`](docs/progress_report.md) を
実装・テスト結果・未決定事項の記録として運用しています。GDD末尾に「今後詰める論点(未決定)」を
明示し、該当する仕様に触れる実装では仕様を勝手に確定させないことを [`CLAUDE.md`](CLAUDE.md) の
ルールとして定義しました。個人開発であっても、仕様変更の追跡可能性とスコープ管理を重視しています。

## 現在の開発状況

村パート(合成・配合・ガチャ・育成・一部施設)とダンジョンパート(半自動戦闘・必殺技・タイプ相性・
ダンジョンツリー)の主要systemは実装済みで、現在も機能追加・バランス調整を継続中です。
バランス値の多くは仮値で、具体的な調整は今後の課題です。
